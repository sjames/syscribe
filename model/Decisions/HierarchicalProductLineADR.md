## Context

Syscribe already has single-model product-line engineering (`FeatureDef`/`Configuration`, the `batsat` SAT engine, `feature-check --deep`, `projection.rs`) and multi-repository composition (§14: `[repos]` + `repoImports:`, which mounts a peer repo's elements into the local qname namespace and resolves cross-repo cross-references by ordinary qname search — "local model first, then each loaded repo in declaration order"). Neither, alone or together, expresses a **product line composed of other product lines**: a prime integrator's `Configuration` that is itself built by picking one already-configured variant from each of several independently-developed, independently-versioned lower-tier product lines (an OEM's vehicle line built from a battery-pack line, an infotainment line, a powertrain line, each maintained by a different team or supplier).

This is a studied problem, not a novel one: **Multiple Software Product Lines (MSPL/MPL)** is the established term for "a product line that results from combining components or products developed from several independent and heterogeneous software product lines" — the textbook example composes `HomeClimateControl`/`HomeFireProduction`/`HomeSecurity` into a `HomeAutomation` product line. **Staged configuration** (Czarnecki et al., 2004/2005) was explicitly extended, in a DaimlerChrysler/TU Berlin research collaboration, to *software supply chains*, using multi-level configuration where a higher stage's context constrains lower stages. Both lines of work converge on the same shape this feature needs.

## Decision

A `Configuration` gains a `subConfigurations:` field: a list of qname/id references to other `Configuration` elements — reachable either locally or, in the common case, via the existing `repoImports:` mounting mechanism from a lower-tier product-line repo. Valid at any tier; naturally empty or absent at a leaf tier (one with no imported lower-tier product lines to consolidate). "Tier" is not a declared schema concept — it falls out structurally from whether a given repo happens to import others, exactly as "leaf" already falls out structurally elsewhere in this codebase (a leaf `Requirement` has no `derivedChildren`; a leaf `PlanningItem` has no `children`).

Four sub-decisions, each with a rejected alternative:

1. **No new cross-repo addressing syntax.** A `subConfigurations:` entry, and every dotted key in `parameterBindings:` that reaches into a consolidated peer, is an **ordinary qname** — reachable because `repoImports:` already mounts a peer's elements into the local namespace (`<package>::<as>`), and `E510`'s existing "circular repo import... directly or transitively" language confirms the loader already walks import chains transitively for cycle detection. *Rejected:* inventing an alias-chained addressing scheme (`repoAlias1::repoAlias2::...::param`) to reach a multi-level-deep descendant — unnecessary once the existing mounting mechanism is recognized as already solving this; a new scheme would just be a worse-integrated duplicate of what `repoImports:` already provides.
2. **`parameterBindings:` is reused verbatim, not replaced or duplicated per `subConfigurations:` entry.** The existing field (a flat map, keyed by the canonical dotted `<FeatureDef qname>.<paramName>` reference) already composes correctly with cross-repo qnames the moment they're mounted; its resolution is simply extended to search the full set of features reachable through `subConfigurations:`, at any depth, not just this model's own local `FeatureDef`s. *Rejected:* a nested `parameterBindings:` scoped to each individual `subConfigurations:` entry — this would fragment one concept (which parameters does this `Configuration` supply values for) across N nearly-identical-looking sub-maps for no resolution benefit, since the dotted key is already globally unambiguous as a qname.
3. **Lower tiers carry zero awareness of anything above them — this is a hard architectural constraint, not just a style preference.** A descendant `FeatureDef` parameter that needs an externally-supplied value declares this exactly as it already would in a single-model `Configuration`: `isRequired: true`, no `default`, `isFixed: false` — a purely local, self-describing declaration with no upward-pointing field. *Rejected:* reusing `bindTo:` (the existing component→system parameter-propagation mechanism) for this purpose — `bindTo:` requires the *lower* tier to name the specific upward parameter path it propagates to (`SystemFeatures::<Feature>::<paramName>`), which is exactly backwards here: it would require every reusable lower-tier product line to be authored with foreknowledge of whoever might someday consolidate it, defeating independent development and reuse (the same lower-tier `Configuration` might be consolidated by zero, one, or many different higher-tier integrators, none of which it can or should know about). `bindTo:`'s existing single-model, component/system semantics are unchanged and out of scope here.
4. **An unbound-and-required parameter left open at an intermediate tier is reported as an opt-in, `--deny`-gateable warning — never a hard error at that tier's own isolated validation.** This is deliberate and load-bearing, confirmed against the transitive-pass-through requirement: a mid-tier `Configuration` may legitimately defer a lower-tier's required parameter further upward (transitive closure across the whole subtree is in scope, not just one level), and a tier being validated in isolation has no way to know whether it is the actual top of some larger hierarchy or will itself be consolidated further by something it has never seen. *Rejected:* a hard error at every tier unconditionally — this would make legitimate, intentional deferral (a package that "must need a configuration" from whoever assembles it, as distinct from a package whose parameters simply carry sensible `default:` values and need no external decision at all) indistinguishable from a genuine defect. *Also rejected:* an explicit "I am the root of the hierarchy" self-declaration field — solves the same problem but adds a new schema concept and a new way to get the model wrong (declaring root-ness incorrectly), when this codebase already has a proven idiom for exactly this shape of problem: `W510`/`W511`/`W512` (multi-repo reproducibility), `W023` (missing implementation path), `W090` (suspect links) are all opt-in, silent by default, surfaced by their own listing commands or promoted to a hard CI gate via `--deny <code>` by whichever repo is actually positioned as the integration point. The same posture applies here with no new mechanism.

## Rationale

- **Why extend multi-repo composition rather than build a separate mechanism?** Because the hard parts — mounting a peer's namespace, resolving qnames across the boundary, transitive import-chain cycle detection — already exist and are already proven. This feature's genuinely new surface is narrow: one new list field, one extended resolution rule for an existing field, and one new completeness check.
- **Why must lower tiers stay unaware of higher tiers?** Independent, parallel development is the entire point of a product-line-of-product-lines: a battery-pack product line is developed once and should be consolidatable by any number of vehicle programs without modification or foreknowledge. A mechanism that required the battery-pack model to name its future consolidator would recreate exactly the coupling multi-repo composition exists to avoid.
- **Why is the completeness check severity-graded by validation context rather than a fixed severity?** Because "open" is not itself a defect — it's the entire mechanism by which staged, multi-party configuration is possible. Only the party that knows it is the actual point of final assembly (because that's the repo they're running CI on) can correctly decide that "still open" now means "genuinely incomplete."

## Consequences

- A model with no `subConfigurations:` anywhere is completely unaffected.
- `bindTo:`'s existing single-model component/system propagation is untouched; the two mechanisms coexist without interaction (a component parameter's `bindTo:` target still resolves purely within its own model, never across a `subConfigurations:` boundary).
- **Explicitly out of scope**, tracked as follow-on only if a concrete need arises: cross-tier `appliesWhen:`/feature-model constraint expressions (a parent's feature gate referencing an individual descendant `FeatureDef` directly, rather than treating a consolidated `Configuration` as a fixed, already-resolved unit); any dedicated browsing/reporting UI for a consolidated hierarchy's full parameter surface beyond what already falls out of existing `show`/`export` once the qnames are mounted; and baseline/release-freezing awareness of a multi-tier consolidation beyond what already exists per-repo.
